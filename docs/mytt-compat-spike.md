# MyTT 兼容 Spike 结论

## 结论

- 当前仓库已具备一层轻量内部兼容路线，足以覆盖本轮策略和因子研究所需范围。
- 本轮不建议引入 `MyTT` 作为运行时依赖，也不建议复制外部源码进入主业务目录。
- 若后续出现明确、低风险、可验证的单指标缺口，优先继续补内部兼容函数，而不是扩大第三方运行时依赖面。

## 引入结论

- 是否引入 `MyTT`：当前结论是否定。
- 原因：现有 `IndicatorService` 已覆盖本轮策略协议、模板元数据和单因子研究接口所需指标与公式兼容函数，继续引入运行时依赖不会显著降低实现成本，反而会增加口径迁移、许可证核查、后续维护和测试基线成本。
- 固定边界：不引入运行时依赖，不复制外部源码，不改变现有策略信号口径，不新增独立 MyTT API 面。

## 与现有指标口径关系

- 仓库当前以 `IndicatorService` 为唯一业务口径来源。
- `IndicatorService` 已承担两类职责：一类是策略与回测直接消费的业务指标口径，如 `RSI / BOLL / KDJ / ATR / OBV`；另一类是面向通达信/同花顺迁移参考的轻量兼容函数与研究指标，如 `REF / HHV / LLV / CROSS / COUNT / EVERY / SMA / BIAS / WR / CCI / BBI`。
- 因子研究层当前通过 `FactorService` 直接复用 `IndicatorService` 计算 `BIAS / CCI / BBI / WR`，这说明当前内部兼容层已经覆盖到“研究型单因子横截面评分”所需范围，无需再暴露额外第三方接口。
- 新增或兼容实现必须保持现有策略信号口径优先，不因为追求 MyTT 形式一致而改变现有交易判断。
- 若将来发现某个 MyTT 公式与当前实现存在差异，应先记录差异，再决定是否单点调整；默认保持现口径。

## 评估结论

- 精度：当前目标是“日线研究口径可解释且固定样本可回归”，不是逐 tick 与所有行情软件完全一致。现有指标和兼容函数已经由 `backend/tests/test_indicators.py` 提供固定样本约束，足以支撑本轮策略和因子研究需求。
- 性能：当前实现为本地 Python 计算，直接运行在已有 bars 序列上。对本仓库现有策略回放、模板展示和 smart selection 单因子排序规模而言，性能已经足够，没有看到必须通过引入 MyTT 换取吞吐的证据。
- 依赖：保持零新增运行时依赖，避免把第三方指标库升级、兼容性和打包问题引入主链路。
- 许可证：既然当前不引入运行时依赖，也不复制外部源码，许可证风险维持在文档评估层面，不进入产品分发面。
- 维护状态：内部兼容层只保留已被当前业务验证的少量函数与指标，维护面更小，回归边界更清晰；相较之下，引入外部公式库会把未来差异追踪和兼容回归扩展到更多未实际使用的能力。

## 状态约定

- 空输入：返回显式状态，例如 `empty_input`
- 历史不足：返回显式状态，例如 `insufficient_history`
- 参数无效：返回显式状态，例如 `invalid_period`
- 可计算：返回 `ok`

本轮已把这类状态补进指标结果结构，避免新增指标只返回 `None` 而无解释。

## 建议

- 继续沿用内部兼容层路线。
- 仅在有真实业务需求、固定样本断言和低迁移风险时单点扩展兼容函数或指标。
- 不把 MyTT 兼容层扩展成新的公开 API 面。
