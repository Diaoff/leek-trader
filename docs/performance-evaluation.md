# 高性能核心评估

## 结论

短期继续使用 Python 路径，不在当前阶段引入 Rust / PyO3 高性能核心。

当前系统基准入口 `GET /api/v1/devtools/system-benchmark` 已覆盖本地 MVP 主链路中的行情质量、回测、报表聚合和风控校验样本。第六批的判断是：已有瓶颈证据还不足以证明跨语言模块的复杂度收益大于维护成本；优先继续优化 Python 内部的数据访问、批处理和算法边界。

## 已有基准覆盖

| 样本 | 覆盖范围 | 当前用途 |
| --- | --- | --- |
| `market_processing` | 日线行情质量报告 | 验证行情数据读取、质量汇总和缺口检查路径 |
| `backtest` | 单标的移动均线回测 | 验证策略信号、成本模型、资金曲线和绩效统计路径 |
| `reporting` | 成交与资产快照分组 | 验证报表指标聚合路径 |
| `risk_validation` | 订单风控校验 | 验证风控检查项、阈值和拒单原因路径 |

基准结果包含 `elapsed_ms`、样本规模和 `summary.total_elapsed_ms`。这些数据适合做本地变更前后对比，不代表生产压测结论。

## 是否引入 Rust / PyO3

当前不引入。只有同时满足以下条件时，再开启跨语言评估：

- 单次回测或指标计算在真实研究样本上稳定超过可接受阈值，例如单标的 5 年日线回测 > 2 秒，或多标的批量回测无法在本地交互窗口内完成。
- Python 侧已经完成明显优化，包括减少 ORM 循环查询、批量读取行情、缓存重复指标、避免重复序列化。
- 瓶颈集中在纯计算内核，而不是数据库 I/O、网络行情源、前端渲染或任务调度。
- 有可复现 benchmark 和回归测试证明跨语言实现与 Python 实现结果一致。

## 优先优化边界

在跨语言之前，优先处理以下 Python 边界：

- 行情读取：批量读取、按 symbol/date 建索引、避免逐条 ORM 循环。
- 回测与指标：将重复计算的技术指标缓存为中间序列，优先用列表/数组批量处理。
- 报表聚合：按账户、日期范围和周期聚合，避免把无关账户或历史全量载入内存。
- 风控校验：保持单订单校验轻量，版本追踪只生成 deterministic 摘要，不引入规则引擎。

## QUANTAXIS / zvt 借鉴边界

本项目只吸收组织方式，不复制实现：

- 从 QUANTAXIS 借鉴账户、交易、行情、任务调度的统一边界命名，避免交易执行和研究回测混在同一服务内。
- 从 zvt 借鉴数据层、因子/策略层、回测层、交易层的分层思路，后续新增模块时优先明确输入输出与持久化边界。
- 不在本地 MVP 阶段引入分布式协议、多账户实盘、复杂数据仓库或外部框架迁移。
- 不用外部项目的实现细节替代本项目已有测试保护的 Python 服务。

## 后续验收标准

- 每次大规模性能改动前后运行 `GET /api/v1/devtools/system-benchmark`，记录样本规模与耗时差异。
- 若提出 Rust / PyO3 方案，必须先附带 Python 基线、瓶颈定位、跨语言边界、等价性测试和回滚方案。
- 只把稳定、纯计算、输入输出清晰的函数纳入跨语言候选，不把数据库 Session、FastAPI route 或业务规则搬入跨语言层。
