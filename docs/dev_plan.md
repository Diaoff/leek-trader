# 模拟炒股系统量化能力升级开发计划

## 1. 背景与报告共识

本计划基于以下三份报告整理：

- `dev_report/report_qwen.md`
- `dev_report/report_longca.md`
- `dev_report/report_doubao.md`

三份报告的共同判断是：当前模拟炒股系统要提升策略可信度，不能只看模拟盘短期收益或胜率，必须建立「数据质量 -> 历史回测 -> 参数验证 -> 风险评估 -> 模拟盘闭环」的研发流程。

报告中反复提到的核心问题包括：

- 数据质量会直接影响信号判断，尤其是复权口径、停牌、ST、涨跌停、缺失值和交易日对齐。
- 缺少可信回测时，模拟盘盈利可能只是运气，不能证明策略有效。
- 均线、MACD、RL baseline 等策略参数需要经过样本内优化和样本外验证，避免过拟合。
- 只看胜率不足以评估策略，需要同时关注最大回撤、收益回撤比、夏普、换手率、手续费和滑点。
- 模拟盘必须尽量贴近 A 股交易规则，尤其是 T+1、涨跌停不可成交、停牌不可交易、交易成本和仓位约束。

## 2. 当前系统基础

当前项目已经具备较多可复用能力，不建议推倒重来：

- 后端已有 Baostock 日线同步能力，数据落在 `market_daily_bars`，并包含复权口径、成交量、换手率、交易状态、估值和 ST 标记等字段。
- 后端已有策略体系，包括双均线、MACD、RL 实验策略、策略运行记录、策略目标解析和模拟下单集成。
- 后端已有量化实验模块，包括 RL 特征、训练、模拟器、奖励函数和训练任务。
- 后端已有 Celery/Redis 任务体系，可承接数据同步、策略运行和后续长耗时回测任务。
- 前端已有策略管理、RL 训练、持仓、订单、组合和行情相关页面，可在现有页面基础上扩展回测和绩效分析。

因此第一阶段不以“替换全部数据源”或“一次性引入完整量化框架”为目标，而是先把现有系统补成可信闭环。

## 3. 8 周开发路线

### 第 1 周：数据质量基线

目标：确保回测和模拟盘使用的数据可解释、可检查、可复现。

任务：

- 基于现有 Baostock 同步服务，补充数据质量检查服务。
- 对每只股票输出同步状态、最新交易日、缺失交易日数量、异常 OHLC、成交量为 0、停牌、ST 标记覆盖情况。
- 明确并文档化当前默认复权口径：Baostock `adjustflag=2` 表示前复权。
- 为 `market_daily_bars` 增加质量报告 API，供前端或开发调试查看。
- 在同步任务完成后生成数据质量摘要，便于发现数据源异常。

交付物：

- 数据质量检查服务。
- 数据质量报告 API。
- 数据同步后的质量摘要。
- 数据质量相关单元测试。

验收标准：

- 能查询单只股票或股票池在指定时间范围内的数据质量。
- 能发现缺失日线、停牌、成交量为 0、ST 标记、异常价格。
- 不影响现有行情接口和策略运行。

### 第 2-3 周：通用回测服务

目标：建立项目内可控的第一版回测引擎，先复用现有策略逻辑和交易规则，不急于引入 Backtrader 或 VectorBT。

任务：

- 新增通用回测服务，输入策略类型、参数、股票范围、起止日期、初始资金、手续费、滑点和仓位限制。
- 回测数据优先读取 `market_daily_bars`，缺失时返回明确错误，不在回测过程中隐式拉取远端数据。
- 复用现有双均线、MACD 和 RL baseline 的信号逻辑，避免回测逻辑与模拟盘策略逻辑分叉。
- 实现 A 股基础交易约束：T+1、停牌不可交易、涨停不可买入、跌停不可卖出、最小交易单位 100 股。
- 输出净值曲线、持仓序列、交易明细、费用明细和基础指标。
- 支持通过 Celery 异步运行长耗时回测任务。

交付物：

- 回测任务创建 API。
- 回测任务状态查询 API。
- 回测结果查询 API。
- 回测结果数据模型或复用现有异步任务模型。
- 单只股票回测和股票池回测测试用例。

验收标准：

- 能对双均线策略跑通单只股票历史回测。
- 能对一个小股票池跑通批量回测。
- 回测结果包含交易明细、净值曲线、最终收益、最大回撤和费用。
- 同一策略参数在回测和模拟盘中使用一致的信号解释。

### 第 4-5 周：策略参数优化与样本外验证

目标：让策略参数从主观配置升级为可验证配置，并控制过拟合风险。

任务：

- 为双均线和 MACD 实现参数网格扫描。
- 支持样本内/样本外时间切分，例如样本内用于寻优，样本外用于验证。
- 支持 Walk-forward 验证，按滚动窗口输出每段最优参数和样本外表现。
- 增加参数结果排名，排序指标默认使用收益回撤比，其次看最大回撤、胜率和交易次数。
- 给策略配置增加“历史验证摘要”，显示该配置是否通过最低验证标准。
- 明确最低验证标准，例如样本外交易次数不少于指定阈值、最大回撤不超过指定阈值、收益回撤比为正。

交付物：

- 参数扫描服务。
- 参数扫描任务 API。
- 样本内/样本外验证报告。
- 策略配置页中的历史验证摘要。

验收标准：

- 能对双均线短周期/长周期做网格扫描。
- 能输出最优参数、样本内表现、样本外表现和过拟合风险提示。
- 样本外不达标的参数不能被标记为“已验证”。

### 第 6 周：绩效与风险评估

目标：从“看胜率”升级为“看风险调整后收益”。

任务：

- 在回测结果中增加专业绩效指标：累计收益、年化收益、最大回撤、夏普比率、胜率、盈亏比、换手率、手续费占比。
- 增加压力测试区间配置，用于观察策略在特定历史阶段的表现。
- 输出月度收益表和年度收益表。
- 输出交易分布统计，包括持仓天数、连续亏损次数、单笔最大亏损和单笔最大收益。
- 暂不强制引入 PyFolio，优先实现轻量内置指标，避免依赖 pandas 版本冲突。

交付物：

- 绩效分析服务。
- 回测结果绩效扩展。
- 前端绩效分析展示区。
- 指标计算单元测试。

验收标准：

- 每次回测都能输出完整绩效指标。
- 能识别“胜率高但回撤大”或“收益高但换手过高”的策略。
- 指标计算有固定样例测试，避免后续改动破坏。

### 第 7-8 周：模拟盘闭环与自动化验证

目标：让历史验证结果真正约束模拟盘运行，形成可迭代闭环。

任务：

- 策略从 draft 到 active 之间增加验证状态约束：未完成历史验证或验证失败的策略默认只能 signal_only。
- 模拟盘下单前复用回测中的交易成本和成交限制配置。
- 自动交易模式下记录策略使用的参数版本和最近一次验证结果。
- 每日收盘后自动执行：数据增量同步、数据质量检查、策略信号计算、模拟盘运行摘要。
- 增加异常提示：数据缺失、策略信号异常、单日交易过多、回测与模拟表现偏离。
- 预留纸面交易 / 仿真账户视图，便于先做长周期验证再进入自动交易。
- 前端展示策略闭环状态：数据就绪、历史验证、模拟运行、风险摘要。

交付物：

- 策略验证状态流转。
- 模拟盘闭环任务。
- 策略运行摘要。
- 前端闭环状态展示。

验收标准：

- 自动交易策略必须能追溯到最近一次通过验证的参数和回测结果。
- 数据质量失败时，策略任务不会静默继续执行。
- 每日任务结束后能看到数据、策略、订单三个层面的摘要。

## 4. 技术方案与取舍

### 数据源

第一阶段继续使用 Baostock 作为主数据源，因为项目已经有同步服务、存储表和测试基础。

AkShare 作为第二阶段候选能力：

- 用于交叉校验 Baostock 数据。
- 用于补充 Baostock 不易覆盖的数据。
- 不在第一阶段替换现有行情链路，避免接口和字段语义大范围变化。

### 回测引擎

第一版实现项目内轻量回测服务，而不是立即引入 Backtrader 或 VectorBT。

原因：

- 当前策略逻辑已经在项目内，需要先保证回测和模拟盘信号一致。
- 外部回测框架会带来数据结构、交易规则和依赖版本适配成本。
- 轻量回测足以支持第一个闭环：历史验证、参数扫描、绩效分析。

后续可以在结果稳定后把回测层拆成两种模式：

- 快速参数筛选：用于网格搜索、样本内筛查和批量预警。
- 规则精确验证：用于单策略、单股票池的完整交易约束回放。

再根据需要增加 Backtrader 或 VectorBT 对比回测。

### 因子与机器学习

Qlib、QUANTAXIS、多因子和 LightGBM 暂列为后续增强，不进入 8 周主线。

第一阶段优先做好：

- 价格与成交量类基础因子。
- 现有策略参数验证。
- RL 实验策略的可解释回测。

### 绩效分析

PyFolio 暂不作为强依赖。

第一阶段先内置核心指标，避免 PyFolio 与 pandas 版本兼容问题影响主系统。

### 4.3 开源项目借鉴

这次参考的开源项目给出的不是单点功能，而是几类可直接借鉴的系统设计：

- `Qlib` 更强调从数据处理、特征、训练、回测到组合与执行的完整链路，适合借鉴为分层架构和流水线式任务组织方式。
- `vn.py` 把交易、回测、纸面交易、数据管理、数据录制和可视化拆开，适合借鉴为“数据层 + 运行层 + 评估层 + 纸面交易层”的模块边界。
- `Qbot` 的价值在于策略、交易和通知联动，适合借鉴为任务完成摘要、异常告警和策略运行状态推送。
- `investing-algorithm-framework` 更接近“事件驱动回测 + 向量化回测 + 指标对比”的组合，适合借鉴为快速筛选和精确验证两套回测模式。
- `roboquant.py` 和 `cryptoquant` 更偏轻量、可组合、支持多市场，适合作为依赖拆分和后续扩展边界的参考。
- `abu` 强调策略与优化监督分离，适合提醒我们不要把参数寻优逻辑和策略执行逻辑耦在一起。

落地到本项目时，优先吸收这些共性能力，不直接照搬外部框架：

- 回测层分成“快速参数筛选”和“规则精确验证”两种模式。
- 数据层补齐历史数据管理、质量检查和导出能力。
- 模拟盘补齐纸面交易、状态追踪、回放和通知机制。
- 评估层补齐结果对比、报告生成和样本外验证。

## 5. API、数据和前端变化

后端建议新增能力：

- 回测任务创建：提交策略、参数、股票范围、时间范围和资金成本配置。
- 回测任务查询：返回任务状态、进度和错误信息。
- 回测结果查询：返回净值曲线、交易明细、持仓、绩效指标。
- 参数扫描任务：返回参数组合排名、样本内表现和样本外表现。
- 数据质量报告：返回股票或股票池的数据完整性与异常摘要。

数据模型建议：

- 可新增回测任务表和回测结果表，也可先复用现有异步任务模型存储结果摘要。
- 大体量净值曲线和交易明细可先以 JSON 存储，后续再拆表优化。
- 每次回测必须保存策略类型、参数快照、数据源、复权口径、交易成本配置和运行时间。

前端建议新增或扩展：

- 在策略页面增加“历史验证”入口。
- 新增回测结果视图，展示净值曲线、交易明细和绩效指标。
- 在策略列表展示验证状态、最近回测时间、样本外表现和风险摘要。
- 在 RL 训练页面保留现有能力，不与通用回测页面混合过深。

## 6. 测试计划

后端测试：

- 数据质量检查：缺失日、停牌、ST、成交量为 0、异常 OHLC。
- 回测执行：无数据、数据不足、正常买卖、涨跌停限制、停牌限制、T+1 限制。
- 交易成本：手续费、滑点、最小交易单位、现金不足。
- 绩效指标：收益、最大回撤、胜率、夏普、换手率使用固定样例验证。
- 参数扫描：短周期小于长周期、非法参数过滤、样本外结果保存。

前端测试：

- 回测任务提交表单参数校验。
- 回测进行中、成功、失败、无数据四种状态展示。
- 策略验证摘要在列表和详情中正确展示。

回归测试：

- 现有策略创建、更新、运行不被破坏。
- 现有模拟下单、持仓、订单、组合接口不被破坏。
- 现有 RL 训练页面和 API 不被破坏。

## 7. 风险与控制

- 胜率提升不能作为硬承诺。计划目标是提升策略评估可信度，用样本外表现和风险指标判断策略是否值得运行。
- 数据源免费接口可能不稳定。第一阶段必须把数据同步失败和数据质量异常显式暴露出来。
- 参数扫描容易过拟合。必须强制样本外验证，并在 UI 中展示风险提示。
- 回测和模拟盘逻辑可能分叉。开发时应优先抽取共享信号解释和交易规则，避免两套逻辑各自演化。
- 大规模股票池回测可能耗时。第一版先支持异步任务和小批量股票池，后续再做缓存和并行优化。

## 8. 后续扩展

8 周主线完成后，再按收益和风险评估结果决定是否扩展：

- 引入 AkShare 作为辅助数据源，实现双源校验。
- 引入 VectorBT 或 Backtrader，作为专业回测框架对比项目内回测结果。
- 引入 QuantStats 或 PyFolio，生成更完整的绩效报告。
- 引入多因子选股和行业/板块过滤。
- 对接更严格的实盘预备流程，包括实盘前检查清单、微实盘验证和风控开关。

## 9. 阶段完成定义

第一版闭环完成的最低标准：

- 数据同步后能看到质量报告。
- 策略上线前能跑历史回测。
- 策略参数能做样本外验证。
- 回测结果能展示收益、回撤、胜率、费用和交易明细。
- 模拟盘自动交易能追溯到最近一次通过验证的策略参数。

达到以上标准后，再评估是否进入多因子、外部回测框架和实盘预备阶段。
