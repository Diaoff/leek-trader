# Leek Trader 总体落地计划（docs 合并版）

## 目标
把 Leek Trader 建成一个可长期运行、可验证、可扩展的本地/私有化量化交易模拟平台，形成完整闭环：

**行情数据 → 数据质量保障 → 股票池筛选 → 策略研究/训练 → 回测评估 → 风控校验 → 模拟交易 → 持仓/资产分析 → AI 复盘 → 监控运维 → 未来 SaaS 预留**

## 计划来源与合并原则
本计划综合以下文档并去重合并：
- `docs/dev_plan.md`
- `docs/optimization-plan.md`
- `docs/report_doubao.md`
- `docs/report_longca.md`
- `docs/report_qwen.md`
- `docs/股票模拟交易系统设计文档.md`
- `docs/量化交易项目评测与功能优化计划.md`

合并原则：
- 先吸收共识，再保留差异化建议
- 先落地主链路，再补增强能力
- 先做 Python 可验证版本，再根据基准决定是否引入 Rust / C++
- 只保留能映射到本项目路线的内容
- 不把外部项目的星数、版本、更新时间当作本项目推进依据

- `☑` 开源许可证决策：Apache-2.0 / MIT / 其他，由项目 owner 明确授权后执行
- `☑` 贡献规范：Issue 模板、PR 模板、代码审查规则、发布流程
- `☑` 数据源使用边界：免费数据源限制、频率、稳定性和免责声明

## 不做事项
- `☑` 不做真实券商交易接入
- `☑` 不做生产级多租户后台
- `☑` 不做过早的大规模架构重写
- `☑` 不做没有基准证据的 Rust/C++ 重写
- `☑` 不做 WebSocket 集群、高可用、负载均衡等生产级实时行情平台
- `☑` 不做 Electron 桌面端，除非 Web 端路线明确不足
- `☑` 不做与最终目标无关的复杂化设计
- `☑` 不做只对标大项目、却无法落地的概念增强
- `☑` 不直接复制许可证不兼容项目代码

## 验收标准
### 每一项任务完成前必须满足
- 功能代码已落地
- 对应测试或验证已执行
- `plan.md` 状态已更新为 `☑`
- 如影响用户可见能力，`README.md` 也已同步
- 未完成缺口已明确写出，不能用模糊表述替代

### 每个阶段完成的标准
- Phase 1：主交易闭环稳定运行，行情和数据质量边界清楚，且各环节可追踪
- Phase 2：研究、回测、复盘链路可用并可查询
- Phase 3：核心异步任务、风控和运行状态可观测、可恢复、可解释
- Phase 4：AI/ML 研究能力可复现、可管理、可解释，不破坏散户易用性
- Phase 5：未来扩展边界清晰，当前单用户逻辑不被污染

## Test Plan
- 后端：`pytest`
- 前端：`cd frontend && npm run build`
- 关键链路：行情 → 数据质量 → 策略 → 风控 → 交易 → 持仓 → 分析
- WebSocket：连接、订阅、推送、断线重连、前端展示
- 回测：历史数据输入、订单撮合、交易成本、绩效指标、报告生成
- 风控：通过路径、拒单路径、阈值配置、拒单原因解释
- AI/ML：训练任务、模型版本、样本外验证、失败恢复
- 新增功能必须补回归测试
- 若涉及数据结构或流程变化，必须补充验证说明

## 长期维护规则
- 任何新增任务先判断是否与已勾选项重复
- 已完成项只允许“修复 / 重构 / 回归增强”，不允许重新开票
- 计划优先按目标链路推进，不按零散页面推进
- 所有后续工作都要能回答：
  1. 属于哪个 Phase？
  2. 推动的是哪条主链路？
  3. 完成后如何验收？
  4. 是否已有性能/质量/用户价值证据？

## Success Definition

- 主交易闭环稳定运行
- 数据质量边界清晰且可观测
- 研究与分析能力可用
- 自动化与复盘能力落地
- 风控、监控与恢复路径明确
- 文档、计划、代码、测试一致
- 后续扩展边界清楚且不返工
