# Leek Trader 下一阶段演进计划（现存报告汇总版）

## 目标

前一版 `docs/plan.md` 中的既定缺口已经完成。本计划重新基于 `docs/` 下现存评测报告，制定下一阶段增量路线：在不重复已完成 MVP 主链路的前提下，把 Leek Trader 从“本地可用、闭环完整”推进到“研究体验更专业、验证更强、运行治理更可持续”。

本阶段仍保持当前定位：本地/私有化 A 股研究与模拟交易平台，不接入真实券商，不提前 SaaS 化，不做生产级多租户或高可用平台。

## 计划来源

本计划吸收并重新筛选当前保留的报告文档：

- `docs/optimization-plan.md`
- `docs/量化交易项目评测与功能优化计划.md`

## 筛选原则

- 不重复实现前一版 `plan.md` 已勾选能力。
- 优先选择报告中仍有明确增量价值、可验证、可回滚的能力。
- 不以外部项目 star 数作为实现理由，只吸收适合本项目定位的设计思想。
- 新依赖默认不引入；如确需引入 MyTT、AData 或通知 SDK，必须单独说明收益、风险、替代方案和验证方式。
- AI、多 Agent、自动交易、多市场、生产监控、多账户等重型方向必须先有边界、验收标准和回滚方案，再进入实现。
- 每批任务必须声明：增量目标、风险点、验收标准、不做范围、需要回归的既有能力。

## 当前基线

### 已完成能力

- 行情、市场总览、新闻、证券目录、历史行情、WebSocket 行情推送。
- 自选股、智能选股、股票池筛选。
- 策略 CRUD、策略模板、策略版本、策略对比、手动运行、`signal_only` / `auto_trade` 执行模式。
- 事件驱动回测、绩效报告、收盘复盘、交易导出。
- 模拟交易、撤单、撮合、风控阈值配置化、风控拒单原因解释、风控规则版本追溯。
- 账户、持仓、成交、收益分析、AI 分析入口。
- RL 训练、模型注册表、模型对比摘要。
- Celery 异步任务框架、任务治理摘要、运行治理页、日志与操作记录基础能力。
- 性能基准入口与高性能核心评估基础。

### 新阶段主要欠缺

- 专业研究体验仍偏轻：技术指标覆盖有限、策略类型有限、回测结果独立分析体验不足。
- 实盘收益分析与回测指标存在体验断层：实盘/模拟报表侧应补夏普、年化、Calmar、基准对比等指标。
- 回测能力仍偏单策略/单标的使用体验：缺组合回测、多标的权重、参数扫描和敏感性分析。
- 前端行情详情维持内嵌页路线；后续只优化内嵌页入口、加载状态和降级提示，不自研 K 线图。
- 运行治理已有面板但缺发布后趋势能力：告警、通知、历史归档和指标阈值仍处于候选规划层。
- AI/LLM 能力仍以单点分析为主，多 Provider、多 Agent、结构化辩论与风控审查仍未进入实现。
- 文档体系只保留少量评测报告，需把现存报告中的候选项统一汇总到本计划，避免继续从旧措辞重复开票。

## 不做范围

- 不接入真实券商交易。
- 不做生产级 SaaS、多租户注册、租户账单、组织管理或细粒度 RBAC。
- 不做分布式高可用、WebSocket 集群、复杂工作流引擎或全局分布式锁。
- 不默认引入 Rust / PyO3、MyTT、AData、TA-Lib、通知平台 SDK、LangGraph 或大模型 Agent 框架。
- 不自研本地 K 线组件；个股详情继续使用内嵌外部详情页作为主要行情图表入口。
- 不让 AI 自动生成不可解释交易代码，不自动修改策略参数，不绕过风控自动下单。
- 不把现存报告中的“当前缺口”直接视为当前事实；所有任务必须重新核对代码现状。

## Phase 6：研究体验与指标体系增强

目标：补齐专业量化研究中最高频、低风险、可回归的体验断点。

### 6.1 实盘/模拟收益高级指标补齐 `☐`

增量目标：在收益分析中补齐与回测一致的关键绩效指标。

范围：
- 后端在报表服务中补充年化收益率、夏普比率、Calmar 比率、收益波动率等指标。
- 前端资产分析页增加对应指标卡和解释文案。
- 指标口径与回测报告保持一致，避免同名指标含义不同。

风险点：
- 初始资金、持仓天数、无风险利率和缺失资产快照会影响计算口径。
- 数据不足时不得展示误导性数值。

验收标准：
- 有资产快照时返回高级指标；数据不足时返回明确的 `null` / 不足原因。
- 前端展示年化、夏普、Calmar 时带有空值兜底。
- 回归覆盖报表摘要、空数据、单日数据和多日数据。

不做范围：
- 不引入复杂组合归因模型。
- 不承诺与第三方平台完全一致的指标口径。

需要回归：
- `backend/tests/test_reporting.py`
- `cd frontend && npm run build`

### 6.2 内嵌行情详情页体验稳固 `☐`

增量目标：继续使用内嵌外部详情页作为 K 线和盘口入口，只补体验兜底，不自研本地 K 线。

范围：
- 保留当前内嵌页路线，优化加载中、加载失败、外部站点不可用时的提示。
- 保留外部打开入口，方便用户在新窗口查看完整行情详情。
- 与本地个股摘要、AI 分析入口、回测/策略入口保持清晰分工。

风险点：
- 外部页面可用性、加载速度和跨域行为不受本项目控制。
- 内嵌页不适合承载本地买卖点标注或自定义指标叠加。

验收标准：
- 个股详情页在内嵌页加载中、加载失败、无 symbol 时均有明确提示。
- 外部打开入口可用。
- 前端构建通过。

不做范围：
- 不自研 ECharts K 线组件。
- 不做本地 MA/MACD/BOLL 叠加图。
- 不做 TradingView 级图表编辑器、分钟线或高频盘口。

需要回归：
- `cd frontend && npm run build`。

### 6.3 回测结果独立展示页 `☐`

增量目标：让回测结果从“摘要可看”升级为“完整可分析”。

范围：
- 新增独立回测结果路由，例如 `/backtests/:id`。
- 展示绩效指标卡、资金曲线、回撤曲线、交易明细和诊断信息。
- 从策略页或回测任务结果跳转到详情页。

风险点：
- 回测任务状态、结果缓存/持久化和页面刷新恢复需要明确。
- 大量交易明细需要分页或虚拟化，避免前端卡顿。

验收标准：
- 完成一次回测后可跳转到详情页。
- 资金曲线、回撤、交易明细和核心指标可见。
- 失败/运行中/结果不存在状态有明确提示。

不做范围：
- 不做多人共享报告、PDF 导出或云端报告中心。

需要回归：
- `backend/tests/test_backtest.py`
- `cd frontend && npm run build`

## Phase 7：策略与指标库扩展

目标：扩展策略研究素材，但保持插件化和可解释，不引入难以维护的大框架。

### 7.1 技术指标服务扩展 `☐`

增量目标：补齐 RSI、BOLL、KDJ、ATR、OBV 等高频指标。

范围：
- 优先用项目内轻量实现或已有工具函数封装指标计算。
- 形成 `IndicatorService` / `IndicatorPlugin` 边界，避免指标逻辑散落在策略中。
- 每个指标提供最小单元测试和边界样本。

风险点：
- 指标公式不同来源存在细节差异。
- 若引入 MyTT，需要先评估许可证、维护成本、依赖体积和结果等价性。

验收标准：
- RSI、BOLL、KDJ 至少 3 类指标可被策略和图表复用。
- 指标计算对空数据、短序列、缺失值有稳定行为。
- 测试覆盖关键公式样本。

不做范围：
- 不一次性搬运 100+ 指标。
- 不引入 TA-Lib 二进制依赖。

需要回归：
- 指标服务单元测试。
- 策略相关测试。

### 7.2 新增可解释策略模板 `☐`

增量目标：基于新增指标补充 RSI、布林带、KDJ 等策略模板。

范围：
- 新增 2–3 个简单、可解释、参数可配置的策略模板。
- 支持回测、手动运行、版本记录和前端创建入口。
- 每个策略输出信号原因和关键指标值。

风险点：
- 策略越多越容易造成 UI 复杂和维护成本上升。
- 指标参数默认值需要保守，避免暗示收益承诺。

验收标准：
- 至少 RSI 和布林带策略可创建、回测、运行并展示信号解释。
- 策略模板有测试和 README/说明同步。

不做范围：
- 不做不可解释黑盒策略。
- 不做收益保证或投资建议。

需要回归：
- `backend/tests/test_strategies.py`
- `backend/tests/test_backtest.py`
- `cd frontend && npm run build`

### 7.3 多信号融合最小版 `☐`

增量目标：支持多个指标/策略信号按可解释权重融合，减少单一指标误判。

范围：
- 设计信号输入结构：方向、强度、置信度、原因、来源策略/指标。
- 实现加权投票或阈值通过的最小融合器。
- 输出融合后的最终信号和参与信号明细。

风险点：
- 融合逻辑容易变成不可解释黑箱。
- 权重过拟合会误导用户。

验收标准：
- 同一标的多个指标能生成融合摘要。
- 融合结果能解释每个子信号贡献。
- 低置信度或冲突信号能给出“观望/无动作”。

不做范围：
- 不做 TradingAgents 式多 Agent 辩论系统。
- 不做自动调权或自学习权重。

需要回归：
- 策略服务测试。
- 风控与订单链路测试，确保融合信号不会绕过风控。

## Phase 8：组合回测与参数优化

目标：把研究能力从单次策略验证推进到参数敏感性和组合层面。

### 8.1 多标的组合回测 `☐`

增量目标：支持多标的、权重和组合资金曲线。

范围：
- 回测入口支持多个 symbol 和目标权重。
- 输出组合收益、回撤、单标的贡献、相关性或权重摘要。
- 前端回测表单增加多标的输入和权重配置。

风险点：
- 多标的交易日不一致、停牌、缺失数据会影响组合曲线。
- 并行回测可能带来资源占用和任务恢复问题。

验收标准：
- 输入 2–3 只股票和等权重，可得到组合资金曲线与指标。
- 单标的数据缺口在结果诊断中可见。
- 组合回测不破坏单标的回测接口兼容性。

不做范围：
- 不做机构级组合优化器。
- 不做实时组合调仓引擎。

需要回归：
- `backend/tests/test_backtest.py`
- 运行治理异步任务摘要测试。

### 8.2 策略参数网格搜索 `☐`

增量目标：让用户能批量比较参数组合，而不是手动试错。

范围：
- 定义参数扫描请求：参数网格、目标指标、排序方向、样本区间。
- 复用异步任务框架运行多次回测。
- 输出参数 × 指标矩阵、最优候选和失败组合原因。
- 前端展示参数扫描结果表和热力图数据。

风险点：
- 计算量爆炸，需要限制参数空间和任务并发。
- 最优参数可能过拟合，必须提示样本外验证。

验收标准：
- 单策略 2 个参数维度可完成小规模扫描。
- 结果包含排序、失败原因和样本外验证提示。
- 参数扫描任务可在监控摘要中观察状态。

不做范围：
- 不做贝叶斯优化、遗传算法或自动实盘调参。
- 不自动写回策略参数。

需要回归：
- 回测测试。
- 异步任务测试。
- AI/ML 参数推荐边界检查。

### 8.3 样本外验证与参数敏感性记录 `☐`

增量目标：把参数扫描、样本外验证和策略退化原因沉淀为可查询历史。

范围：
- 持久化每次参数扫描/样本外验证的数据范围、指标、通过/失败原因。
- 在策略或模型详情页展示验证历史。
- 提供退化原因和人工复核入口。

风险点：
- 存储结构过早复杂化。
- 历史验证数据与策略/模型版本关系需要清晰。

验收标准：
- 同一策略或模型可查询多次样本外验证结果。
- 每个窗口能追溯数据范围和指标。
- 验证任务失败不影响行情、交易、持仓主链路。

不做范围：
- 不做自动重训闭环。
- 不做外部 MLOps 平台集成。

需要回归：
- 策略、回测、参数扫描相关测试。

## Phase 9：运行治理与通知增强

目标：在不做生产级监控平台的前提下，补发布后运行反馈能力。

### 9.1 运行指标历史归档与趋势 `☐`

增量目标：让运行治理从“当前状态”升级到“短期趋势”。

范围：
- 定期保存核心运行指标快照：行情新鲜度、策略成功率、交易成功率、任务失败率。
- 运行治理页展示最近 N 次或最近 N 天趋势。
- 保留清理策略，避免本地数据库无限增长。

风险点：
- 指标口径变化会影响历史可比性。
- 不应把本地趋势能力包装成生产监控。

验收标准：
- 能查看最近一段时间指标趋势。
- 指标快照有保留周期或数量上限。
- 当前 JSON 指标接口保持兼容。

不做范围：
- 不接入 Prometheus/Grafana。
- 不做长期归档或 SLA 报告。

需要回归：
- `backend/tests/test_monitoring.py`
- `cd frontend && npm run build`

### 9.2 本地通知与告警最小版 `☐`

增量目标：对关键事件提供可选通知，减少用户反复盯页面。

范围：
- 事件类型：回测完成、异步任务失败、数据质量异常、策略有效信号、风控拒单异常增多。
- 首期优先提供应用内通知或本地日志通知。
- 外部邮件/企业微信/WebHook 只做接口边界，不默认接入。

风险点：
- 通知过多会变成噪音。
- 外部通知涉及密钥和隐私，不能默认开启。

验收标准：
- 关键事件可在运行治理页或通知列表看到。
- 通知有已读/清理或保留策略。
- 敏感字段不进入通知明文。

不做范围：
- 不做短信、电话、企业告警平台。
- 不默认接入外部 WebHook。

需要回归：
- 监控、异步任务、日志操作记录测试。

### 9.3 高风险操作记录扩展 `☐`

增量目标：把新增高风险操作纳入操作记录。

范围：
- 参数扫描启动、策略参数采纳、模型启用/停用、通知配置变更等操作写入 `audit.log`。
- 操作记录事件继续脱敏敏感字段。
- 发布清单同步操作记录验证步骤。

风险点：
- 操作记录字段不稳定会增加后续兼容成本。
- 不应把本地操作记录误当合规操作记录。

验收标准：
- 新增高风险操作有操作记录事件。
- 操作记录事件包含 actor、tenant、resource、outcome 和脱敏 details。
- 普通用户不能执行超级用户操作。

不做范围：
- 不做不可抵赖签名、集中采集、审批流或长期归档。

需要回归：
- 操作记录相关测试。
- 权限链路测试。

## Phase 10：数据源与市场范围评估

目标：谨慎评估数据源和市场扩展，不破坏现有 A 股主链路。

### 10.1 数据源增强评估 `☐`

增量目标：评估是否需要引入 AData 或其他数据源补足资金流/基础面/多市场字段。

范围：
- 先写评估记录：许可证、维护状态、接口稳定性、字段覆盖、失败模式、缓存策略。
- 做只读 provider spike，不接入主链路。
- 对比现有 provider 能力，明确新增价值。

风险点：
- 新数据源格式和频率限制不稳定。
- 多 provider 会增加数据一致性和排障成本。

验收标准：
- 输出数据源评估文档和最小 spike 结果。
- 明确是否值得进入正式集成批次。
- 不影响现有行情、历史数据和质量报告。

不做范围：
- 不直接把新 provider 设为主源。
- 不为了字段丰富牺牲稳定性。

需要回归：
- 行情 provider 测试。
- 数据质量测试。

### 10.2 港股/美股扩展预研 `☐`

增量目标：明确多市场扩展所需模型、接口和 UI 改动，不直接铺开实现。

范围：
- 梳理 symbol 规范、交易日历、币种、时区、行情字段和数据源差异。
- 评估账户、持仓、订单、报表是否需要币种和市场维度。
- 产出迁移影响清单。

风险点：
- 多市场会放大数据质量、交易日历、汇率和税费复杂度。
- 过早实现会污染当前 A 股本地主链路。

验收标准：
- 形成多市场预研文档。
- 明确哪些模型/接口需要扩展，哪些当前不能动。
- 给出是否进入实现的 go/no-go 判断。

不做范围：
- 不新增港美股交易能力。
- 不承诺多币种账户或跨市场组合收益。

需要回归：
- 无代码实现时仅需文档一致性检查。

## Phase 11：架构债与可维护性治理

目标：降低后续扩展成本，避免策略、回测和前端页面继续膨胀。

### 11.1 策略服务边界拆分评估 `☐`

增量目标：评估并逐步拆分过大的策略服务职责。

范围：
- 梳理策略管理、信号计算、运行调度、版本记录、回测适配的边界。
- 先写拆分方案和回归保护，再做小步迁移。
- 保持 API 和测试行为不变。

风险点：
- 拆分服务容易引入行为回归。
- 与回测、异步任务、风控链路耦合较多。

验收标准：
- 有清晰职责图和迁移顺序。
- 每次迁移都有测试保护。
- 对外 API 不破坏。

不做范围：
- 不做大爆炸重构。
- 不引入通用 Repository 或复杂领域框架。

需要回归：
- 策略、回测、订单、异步任务测试。

### 11.2 回测 Job 持久化评估 `☐`

增量目标：解决进程内 Job 注册表在重启、多进程下的恢复风险。

范围：
- 评估把回测 Job 状态迁移到数据库或 Redis 的收益和成本。
- 明确状态机：queued/running/succeeded/failed/cancelled。
- 保留已有查询接口兼容性。

风险点：
- 状态迁移会影响前端轮询和旧任务查询。
- Redis/数据库选择会影响部署复杂度。

验收标准：
- 输出持久化方案或实现最小 DB 状态表。
- 服务重启后可查询已完成/失败任务的基本状态。
- 旧接口兼容。

不做范围：
- 不做完整工作流引擎。
- 不做跨节点调度。

需要回归：
- 回测任务测试。
- 异步任务治理测试。

### 11.3 现存报告汇总与索引 `☐`

增量目标：让现存报告中的候选项都被本计划吸收、归类或明确暂缓。

范围：
- 建立 `docs/index.md`，区分当前计划与现存评测报告。
- 在索引中说明 `optimization-plan.md` 与 `量化交易项目评测与功能优化计划.md` 是候选来源，不是当前事实清单。
- 把保留/暂缓/不做项汇总到本计划。

风险点：
- 报告中部分描述已过时，不能直接作为实现状态。

验收标准：
- 读者能快速知道当前执行计划是 `docs/plan.md`，两份报告是候选来源。
- `docs/plan.md` 与 `README.md` 描述一致。

不做范围：
- 不重写所有历史报告正文。

需要回归：
- 文档一致性检查。

## 验收规则

每个批次完成前必须满足：

- 已声明增量目标、风险点、验收标准、不做范围、需要回归的既有能力。
- 已确认不重复前一版已完成计划项。
- 已补或更新对应测试；无测试框架的前端变更至少运行 `cd frontend && npm run build`。
- 已运行后端相关测试，至少覆盖被影响服务。
- 已更新 `README.md` 或当前保留文档中受影响内容。
- 已执行 `git diff --stat` 和模块化 diff 复核，确认未越界。

## 通用测试矩阵

- 后端全量：`pytest`
- 后端定向：按变更模块运行 `backend/tests/test_*.py`
- 前端构建：`cd frontend && npm run build`
- 权限链路：普通用户与超级用户访问监控、任务、配置和高风险接口
- 风控链路：通过路径、拒单路径、规则版本、拒单原因解释
- 回测链路：单标的、组合、失败任务、结果查询、绩效指标
- AI/LLM 链路：训练、验证、参数建议、失败恢复、多 Provider/Agent 边界
- 文档一致性：`README.md`、`docs/plan.md`、现存评测报告

## 成功定义

下一阶段成功不是“堆更多功能”，而是同时满足：

- 研究体验更专业：指标、内嵌行情详情体验、回测结果、策略模板更完整。
- 验证能力更强：组合回测、参数扫描、样本外验证明细可追踪。
- 运行反馈更及时：趋势、通知、操作记录覆盖新增高风险操作。
- 架构仍可维护：不引入不必要依赖、不大爆炸重构、不污染本地单用户主链路。
- 文档状态清晰：当前计划与现存评测报告不再混淆。
